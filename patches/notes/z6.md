Upstream 3bab23c reports three device losses with page faults in textures made and shown in the previous tenth of a second. That is upstream evidence, not a demonstrated Comet cause. It delays publication until upload completion, using neutral 1x1 or previous view of the same texture. Comet currently exposes many new copies on the heap path before recording/submission; the experiment narrows that window for accepted first uploads. No claim that this alone fixes black albedo or device removal.

## Invariants and adaptation

- Start with placed, single-slice/single-sample 2D SRVs only, fully readable source, no RT/DS/UAV, no alias, host-written or already-staged copy. Require fresh COMMON state. No new ahead claim during M4 preflight or on a full card; an already-made job can be polled while full. Rejected/partial/ordinary updates keep normal behavior.
- A mutex/condvar gate per HostTexture arbitrates Fresh/Pending/Ready/Listed/Failed. Accepted copies cannot be exposed by another descriptor writer or recorded in a regular list before the worker confirms the fence. Normal use marks the resource Listed. Jobs own both the Arc<HostTexture> and their private Arc<Staging>. COPY queue implicit promotion/decay is used only from COMMON; the regular list state tracker is unchanged.
- Two workers, separate allocators/lists/fences, shared COPY queue. Cap queued/in-flight source + staging bytes at 96 MiB; batch target 16 MiB / 64 jobs, with one larger admissible job allowed. Allocation happens before admission, so the cap is a charged-job cap, not a strict peak process allocation cap. A full snapshot is read under the existing remap guard, detiled outside it; incomplete snapshot takes normal fallback.
- Fence value must be reached and not device-removed sentinel. No worker writes the descriptor heap. Accepted jobs expose Ready only after their copy completed. Heap poll uses generation-key validation, so a changed title slot does not receive an old flip. Hash the exact snapshot in the same window/full-span mode as N5; retain regular recheck scheduling. Typed null is used rather than upstream gray 1x1 because Comet has a typed-null path already.
- Both pool switches remain independent. Host texture still originates in resource::host_copy (including R3 shared heaps). The extracted build_staging uses the existing staging allocator including COMET_STAGING_POOL, and record_subresource adds staging.base to the copy footprint on both queue paths. The job pins its slice through the COPY fence; no slice is returned on an unproved submission. Current R3 pool does not reuse placed offsets. Any future tiled/reserved or reused alias backing needs a separate eligibility/lifetime audit.
- Pre-submit copy failure returns jobs to ordinary uploads; post-submit unproved fence disables ahead and intentionally retains affected resource/staging/worker allocations, marks Failed, and never publishes them. This is fail-closed process-lifetime quarantine, not recovery. May consume memory until restart. No GPU-wide wait added to the background pass, but a normal table/transition encountering Pending can wait on the worker; measure contention. If a worker hangs without returning, those waits may also hang.
- Scope limitation: this pairs show-after with the **accepted ahead first-upload path**, not a complete port of upstream ordinary graphics-list VICTORY_SHOW_AFTER or global asynchronous FLIPS. Declined and subsequent normal uploads retain existing publication timing; the heap poll can delay visible readiness by one or more passes. In particular this is not a claim that every slot in Comet now has fence-gated publication. Neutral is typed null, not upstream's gray texture.
